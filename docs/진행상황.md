## 과거 작업 로그 — 현재 운영 상태보다 우선하지 않음

Phase 0~4가 끝난 뒤, 코드를 다시 훑어보다 **치명적 공백**을 하나
발견해서 사용자에게 제안했고, 사용자가 제안 목록 전부를 구현하라고
지시함. 아래 순서대로 진행 중.

> 아래 기록의 마이그레이션 미적용 안내는 2026-08-16에 해소됐다. 현재
> `0001`~`0017`은 원격 이력과 실제 스키마 대조를 마친 상태다.

### 1. [완료] 기준정보 관리 화면 — 발견한 치명적 공백

지금까지 학급·특별실·교과·학생 데이터는 **데모 시드로만** 만들어졌고,
실 학교가 이 데이터를 넣을 화면이 전혀 없었다. 예약·시간표·결보강·
예산·PBS 전부 이 데이터를 쓰는데 채울 방법이 없던 셈이다. `/admin/data`
에 부서·교과·학급·특별실·학생 5개 탭 CRUD를 추가해서 메웠다. 새
마이그레이션 없이 기존 RLS(0001_core.sql의 same_school+is_admin
정책)를 그대로 씀. 학교 관리 화면에 학급·특별실이 0개면 경고 배너 표시.

### 2. [완료] 앱 안 알림(벨 아이콘)

결보강 배정·특별실 예약 승인/반려·지출 승인/반려 시 당사자에게 알림.
`notifications` 테이블 + Realtime. **웹푸시·이메일은 의도적으로
뺐다** — VAPID 키·서비스워커·구독 관리가 또 한 덩어리라 범위를
나눴다. 필요하면 다음 세션에서 웹푸시를 이 위에 얹으면 된다(알림을
만드는 지점인 `lib/notifications.ts`의 `notify()`는 이미 있으니,
거기서 web-push 발송을 추가로 부르기만 하면 됨).

**실제로 버그를 하나 잡음.** 벨을 데스크톱 사이드바·모바일 상단바
두 곳에 동시에 두면서 각자 따로 Supabase Realtime을 구독하게
짰더니 "cannot add postgres_changes callbacks after subscribe()"
런타임 오류가 났다 — 같은 채널 토픽(`notifications:{profileId}`)을
두 인스턴스가 동시에 subscribe() 해서 생긴 충돌. **devpreview-temp +
Playwright로 실제 렌더링을 확인하다가 발견함** — tsc·eslint·build는
전부 통과한 상태였는데도 브라우저에서는 애플리케이션 에러가 나고
있었다. 알림 목록·구독 로직을 `AppShell`(공유 부모) 한 곳으로
올리고, `NotificationBell`은 props만 받는 순수 표시용 컴포넌트로
바꿔서 고침. **이번 세션에서 스크린샷 검증이 실제 버그를 잡아낸
사례** — 매번 습관적으로 하던 절차가 헛수고가 아니었다는 뜻.

### 3. [완료] 학생 안전 프로토콜 카드

`safety_protocols` 테이블(0011_safety.sql) + `/support/safety`. 조회는
학교 전체(응급 시 담임 아니어도 봐야 함), 쓰기는 관리자만. 본문은
PBS와 같은 방식으로 암호화. 학생 이름·학급 검색 + 분류별 색 배지.

### 4. [완료] 세션 타임아웃 실제 적용

`SESSION_TIMEOUT_MIN` 상수가 정의만 있고 안 걸리던 걸
`middleware.ts`에서 httpOnly 쿠키(`ha_activity`)로 실제 구현.
경로 민감도별(일반 120분/학생지원 20분/외부AI 60분) 제한 시간을
넘기면 자동 로그아웃 + `/login?reason=timeout`.

### 5. [완료] 데모 데이터 — 특별실 예약 무작위화 + 학생 안전 프로토콜 표본

사용자 요청: "데모 데이터에서 특별실이 무작위로 잡혀있도록 하고 학생데이터도
더미로 넣어". `lib/demo/seed.ts`의 특별실 예약이 예약 30건을 손으로 하나하나
지정한 고정 목록(`bookingPlan`)이었어서, 캘린더를 앞뒤로 넘겨보면 앞쪽 며칠
말고는 비어 보였다. 방 유형별로 어울리는 과정·사유 후보
(`ROOM_BOOKING_PROFILE`, `lib/demo/seed-data.ts`)를 두고, 평일 -14일~+24일
(약 5주 반)을 방마다 8~14건씩 무작위로 채우도록 바꿨다. 실행할 때마다 다른
조합이 나오지만 같은 방·같은 시간대 겹침은 여전히 `overlaps()`로 막는다
(겹치면 DB 이중예약 방지 제약에 걸려 시드 전체가 실패하기 때문). 고교학점제
선택과목(바리스타 그룹) 충돌 시연용 예약은 그대로 남겨 두고 무작위 생성보다
먼저 자리를 잡게 해서 우선순위를 지켰다.

학생 안전 프로토콜(`safety_protocols`, `/support/safety`)은 지금까지 시드에
전혀 없어서 데모에서 빈 화면으로만 보였다 — PBS 기록은 표본이 있었는데 이건
빠져 있었다. 발작·알레르기(견과류/갑각류)·연하곤란(다진 음식/걸쭉한 음료)·
기타(휠체어 이동/큰 소리 반응) 7종 템플릿(`SAFETY_PROTOCOL_TEMPLATES`)을
학생 7명 중 1명꼴로 배정, PBS와 같은 방식으로 `encryptSecret()` 암호화해
저장. `SeedSummary`에 `students`·`safetyProtocols` 카운트를 추가하고
`/setup` 시드 완료 화면에도 표시.

**검증**: tsc·eslint·vitest(59개)·build 전부 통과. Gemini/Supabase 네트워크가
없는 샌드박스라 실제 시드 실행 자체는 못 해 봤음 — 배포 후 `/setup`에서
한 번 돌려 특별실 예약이 여러 날짜에 분산되는지, 안전 프로토콜 카드가
뜨는지 확인 필요.

### 6. [완료] 정규 시간표 엑셀 업로드 — 발견한 또 하나의 치명적 공백

코드를 훑다가 `timetable_slots`(정규 시간표)를 채우는 화면이 앱 어디에도
없다는 걸 발견함 — `grep -rln "timetable_slots" app/`로 확인하니
`substitutions/actions.ts`에서 **읽기만** 하고, 쓰는 곳이 전무했다. 데모
학교만 시드로 채워져 있었고, 실제 학교는 시간표 자체를 넣을 방법이
없었던 셈이다(`/timetable` 페이지의 빈 상태 문구 "관리자가 시간표를
올리면 여기에 나옵니다"가 애초에 이 기능을 전제하고 쓰여 있었음 — 안
만들어져 있었을 뿐).

기존 계획 문서의 "엑셀/CSV 업로드"가 원래 겨냥하던 것과 정확히 같은
빈 자리라 이번 "엑셀 업로드" 항목을 여기 씀. 부서·교과·학급·특별실·
학생은 이미 `/admin/data` 화면으로 하나씩 등록 가능해서 굳이 대량
업로드가 필요하지 않지만, 시간표는 교시 수만큼(학급당 주 20~30칸)
손으로 치는 게 비현실적이라 이게 진짜 필요한 자리였다.

**구현**: `/admin/data` 6번째 탭 "시간표 업로드".
- `lib/import/timetable.ts` — 파싱된 행을 검증하는 순수 함수
  (`parseTimetableRows`). exceljs 의존성이 없어 vitest로 그대로
  테스트함(`tests/unit/timetable-import.test.ts`, 14개 케이스: 없는
  학급/요일/교시/교사, 교사 이름 중복(모호), 협력교사=담당교사, 파일
  안 중복, 같은 교사 시간 겹침 — 특히 **과정별 시정이 달라도(초등
  2교시·중학 2교시처럼) 실제 겹치는 시각을 잡아내는지**는 이 세션
  다른 곳(시드 스크립트)에서 실제로 버그가 났던 유형이라 꼭 넣음)
- `lib/import/timetable-xlsx.ts` — exceljs로 실제 파일 읽기/양식 만들기
  (`'server-only'`, 파싱 로직과 분리해 위 파일만 순수하게 테스트 가능)
- `app/(app)/admin/data/timetable-actions.ts` — 미리보기/반영 두
  서버 액션. **같은 파일을 두 번 보낸다** — 미리보기 결과를 서버가
  세션에 들고 있다가 반영 시점에 그걸 그대로 믿는 구조보다, 반영

### 7. [완료] IEP(개별화교육계획) 목표·진도 관리

`iep_goals`·`iep_progress` 테이블(0012_iep.sql) + `/support/iep`. PBS·안전
프로토콜과 같은 "학생 지원" 구역이라 `student_sensitive` 등급(진입 경고·
상시 배너·20분 세션 타임아웃)이 자동으로 걸린다 — `lib/security/
sensitivity.ts`에 이미 `planned: true`로 자리만 잡혀 있던 메뉴 항목이었고,
이번에 그 플래그를 지웠다.

**스키마**: 목표(`iep_goals`) 하나에 진도 기록(`iep_progress`) 여러 건이
달리는 구조 — PBS(행동유형 하나에 기록 여러 건)와 같은 모양이다. 목표는
영역(자조/의사소통/학습/사회성/운동/기타)·목표 문장·학기 라벨·상태
(진행중/달성/중단)를 갖는다. 진도는 달성도 4단계(독립수행/부분도움/
전체도움/미수행)와 선택적 메모를 갖고, 메모는 PBS·안전 프로토콜과 같은
방식으로 `encryptSecret()`으로 암호화해 저장한다.

**RLS는 PBS 쪽을 따랐다** — 안전 프로토콜(관리자만 작성, 응급 시 전원이
봐야 함)보다는 PBS(교사가 직접 기록하는 개인 기록)에 더 가깝다고 판단해서,
조회는 학교 전체(협력수업·치료지원 교사도 같은 학생 목표를 봐야 함),
작성은 누구나(작성자 = `created_by`/`recorded_by`), 수정·삭제는 작성자
본인 또는 관리자로 좁혔다. 목표를 지우면 딸린 진도 기록도
`on delete cascade`로 함께 지워진다.

**UI**: PBS의 "학급 → 학생(가명) → 탭 한 번" 흐름을 그대로 가져왔다.
학급·학생을 고르면 그 학생의 목표 카드가 나오고, 카드마다 달성도 버튼
4개 중 하나를 누르면 그 자리에서 바로 진도가 기록된다(PBS의 행동유형
탭과 동일한 패턴). 기록 직후 "메모 붙이기"로 짧은 메모를 붙일 수 있는
것도 PBS의 "자세히 적기" 2단계 패턴을 그대로 재사용했다. 별도 그래프는
만들지 않았다 — 대신 최신 기록과 바로 이전 기록의 달성도 점수를 비교해
"▲ 좋아지는 중 / ▬ 제자리 / ▼ 주춤" 배지 하나로 추세를 보여준다
(`lib/iep/progress.ts`의 `progressTrend()`). PBS 트렌드 차트보다 훨씬
단순한 지표라 막대그래프까지는 과하다고 판단했다(범위 지시사항의
"차트는 꼭 필요한 경우가 아니면 넣지 않는다"를 따름).

**순수 함수 하나를 빼서 테스트**: 진도 기록을 목표별로 묶고 목표 안에서
날짜 역순으로 정렬하는 로직(`groupProgressByGoal`)과 추세 판정 로직
(`progressTrend`)을 `lib/iep/progress.ts`에 순수 함수로 분리해
`tests/unit/iep-progress.test.ts`(10개 케이스)로 테스트했다. 화면
데이터를 만드는 `page.tsx`도 이 함수를 그대로 써서, 로직이 테스트와
실제 화면에서 갈라지지 않게 했다.

`lib/security/audit.ts`에 `iepGoalCreate`·`iepGoalView`·
`iepProgressCreate` 추가(조회 자체도 PBS·안전 프로토콜과 같은 원칙으로
감사로그에 남김).

**데모 시드**: 학생 5명 중 1명꼴로 목표 2개씩(`IEP_GOAL_TEMPLATES`,
`lib/demo/seed-data.ts`), 목표마다 최근 4주간 진도 기록 3건을 "전체도움 →
부분도움 → 독립수행"으로 점점 나아지는 순서로 채워 넣어서, 데모를
열자마자 "▲ 좋아지는 중" 배지가 보이게 했다. `SeedSummary`에 `iepGoals`
카운트를 추가하고 `app/setup/seed-panel.tsx` 시드 완료 화면에도 표시.

**사용설명서**: "8. IEP 목표" 절을 새로 넣고(안전 프로토콜과 쉬운글
안내문 사이), 이후 절 번호를 9→15까지 한 칸씩 밀었다. 목차·본문 내

### 8. [완료] Playwright e2e 테스트

`playwright.config.ts` + `tests/e2e/` 4개 스펙(9개 테스트)을 새로 만듦.
계획서에 있던 흐름을 그대로 구현: 로그인(성공/실패/로그아웃) →
특별실 예약(빈 칸 예약 + 충돌 차단) → 학사일정 등록(전교 행사 +
아무것도 안 넣고 닫기) → 결보강(결과 신청 + 관리자 배정).

**설계에서 신경 쓴 것**
- 데모 학교는 매일 새벽 자동 초기화되고 여러 사람이 "체험하기"로
  동시에 들어올 수 있는 **공유 환경**이다. 그래서 "이 방·이 시간은
  비어 있다" 같은 고정 전제를 두지 않고, 화면에서 실제로 "비어
  있음"인 칸을 찾아 그 자리에서 예약하고, 충돌도 테스트가 직접
  만들어서(같은 학급을 같은 교시·다른 방에 또 예약 시도) 검증하는
  방식으로 짰다 — 특정 방 이름이나 날짜에 의존하지 않아 데모 데이터가
  어떻게 무작위로 채워져 있든 돌아간다
- 결보강 신청 결과 메시지는 그날 그 교사의 시간표에 수업이 있는지에
  따라 "보강이 필요한 수업 N개를 찾았습니다"와 "보강 대상은 없습니다"
  두 갈래로 갈리는데, 어느 쪽이든 "신청 자체는 성공했다"는 뜻이라
  둘 다 통과로 봄
- 관리자 배정 테스트는 배정 대기 중인 결보강 건 자체가 없을 수 있어
  `test.skip`으로 건너뛰게 함(데모 데이터 상태에 좌우되는 부분이라
  실패로 처리하면 안 됨)
- `AppShell`의 사이드바(`bodyBlock`)가 데스크톱·모바일 두 벌로 렌더링될
  수 있다는 걸 이 세션 초반에 알림 벨 버그로 이미 알고 있어서,
  `nav`·"로그아웃" 같은 공용 UI 요소는 처음부터 `.first()`로 스코프해
  Playwright의 strict-mode(여러 개 매치 시 에러) 위반을 피함
- e2e 스펙은 Playwright 자체 컴파일러(esbuild)로 돌아 `tsconfig.json`의
  `@/*` 경로 별칭을 못 타므로, 데모 계정 정보(`tests/e2e/demo-accounts.ts`)
  는 `lib/demo/seed-data.ts` 값을 리터럴로 옮겨 적었다(설정 복잡도보다
  약간의 중복을 택함)

**검증 한계**: `npx playwright test --list`로 9개 테스트가 전부
정상적으로 컴파일·탐지되는 것과 `eslint`는 확인했지만, **실제로 통과
하는지는 확인 못 했다** — 이 세션 샌드박스에는 진짜 Supabase 백엔드가
없어서(로그인 자체가 안 됨) 끝까지 돌려볼 수 없었다. 실제 배포본이나
`.env.local`이 채워진 로컬 dev 서버(데모 학교가 시드된 상태)를 대상으로
`npm run test:e2e` 또는 `E2E_BASE_URL=... npm run test:e2e`를 한 번
돌려서 실제 통과 여부를 확인해야 한다.

**SEC-01/02 — RLS는 행 단위만 막는다는 구조적 허점.** `profiles_update_self`
정책이 `WITH CHECK` 없이 `USING (id = auth.uid())`만 검사해서, 로그인한

새 마이그레이션 `supabase/migrations/0014_rls_hardening.sql`로 열 단위
방어를 추가했다:
- `guard_profiles_update()` 트리거 — `school_id`는 관리자 포함 누구도 못
  바꿈(실제로 이 컬럼을 UPDATE로 바꾸는 앱 코드가 없음을 확인). 관리자가
  아니면 `role`·`is_active`·`employment`·`department_id`·`work_days`도
  못 바꿈(self-update가 실제로 쓰는 필드는 키·토큰류뿐이라 영향 없음).
- `guard_reservation_update()` 트리거 — 관리자가 아닌 요청자는 `status`를
  `cancelled`로 바꾸는 것 외엔 아무 컬럼도 못 바꿈
  (`cancelReservation()`이 실제로 하는 일과 정확히 일치).
- `budget_expenses_update_owner`, `substitution_respond` 정책은 **삭제**.
  앱 코드 전체를 확인한 결과 두 정책 다 실제로 쓰는 화면이 없는 죽은
  정책이었다(지출 취소는 별도 DELETE 정책이 담당, 결보강 자기-수락 화면

### 12. [완료] 결보강 배정 기준 화면 레이아웃 깨짐 수정

사용자가 실제 배포(`hanarum.vercel.app/admin`)의 "결보강 배정 기준" 카드
스크린샷을 보내옴 — 라벨 텍스트("시간강사 우선", "시간강사에게 먼저
배정" 등)가 단어 하나하나 세로로 줄바꿈되며 숫자 입력창과 겹쳐 보였다.

원인: `WeightsForm`·`MonthPicker`가 `` `${inputClass} w-20` `` 처럼
템플릿 리터럴로 클래스를 이어붙였는데, `inputClass`(`components/ui.tsx`)
자체에 `w-full`이 들어 있다. 같은 유틸리티 레이어의 두 너비 클래스가
같이 있으면 살아남는 쪽은 클래스 나열 순서가 아니라 **Tailwind가 CSS를
생성한 순서**로 정해진다 — 이번엔 `w-full`이 이겨서 입력창이 행 전체
너비를 차지했고, 그 결과 라벨 텍스트 칸이 거의 0으로 밀려 단어마다
줄바꿈된 것.

이미 저장소에 있는 `cn()`(`lib/cn.ts`, clsx + tailwind-merge)으로
바꾸면 tailwind-merge가 충돌하는 유틸리티를 감지해 마지막에 오는 클래스
쪽을 확실히 이기게 해 준다. `weights-form.tsx`·`payroll/month-picker.tsx`
두 곳을 `cn(inputClass, 'w-20 ...')` 형태로 고침. 같은 `${inputClass} w-`
패턴이 코드베이스에 더 있는지 전수 검색했고, 이 두 곳 말고는 전부
`inputClass`를 단독으로 쓰거나(너비 충돌 없음) `bg-surface`처럼 같은
값을 중복 지정하는 무해한 경우였다.

**검증**: `devpreview-temp` 임시 라우트로 `WeightsForm`을 렌더링해
Playwright 스크린샷으로 수정 전/후 비교(라벨·힌트·입력창이 각자 제자리에
나옴을 확인) — 사용자가 보낸 스크린샷과 같은 뷰포트 폭에서 재현한 뒤
고쳤다. tsc·eslint·vitest·build 전부 통과.

### 13. [완료] 실제 학교가 등록돼 있어도 데모 시드를 허용

사용자가 "체험하기"를 눌러도 반응이 없다고 보고 → 원인을 좁혀가다가
`/setup`에서 데모 데이터 만들기를 눌러보니 `실제 학교(청암학교)가
등록돼 있어 데모 시드를 돌리지 않습니다`라는 명시적 거부 응답을
확인함(`app/api/demo/seed/route.ts`에 원래 있던 안전장치 — 실제 학교가
하나라도 있으면 409로 거부). 즉 "체험하기" 버튼이 안 눌린 게 아니라
애초에 **데모 학교 자체가 한 번도 만들어진 적이 없었던 것**(청암학교를
먼저 등록해서 이후 데모 시드가 막힌 상태).

사용자에게 "같은 배포에 데모 허용" vs "별도 프로젝트로 분리" 중 선택을
물었고, **"학교들이 등록되어 있어도 데모는 체험할 수 있어야 한다"**는
답을 받아 가드를 제거함.

`seedDemoSchool()`(`lib/demo/seed.ts`)이 실제로 건드리는 대상을 다시
확인했다 — 정리 단계에서 지우는 건 `@hanbit.demo`로 끝나는 auth 계정과
`schools.is_demo=true` 행뿐이고, 새로 만드는 것도 전부 그 안에서
`school_id`가 새로 발급된 데모 학교로만 들어간다. 실제 학교의 `school_id`
와 절대 겹치지 않는 구조라, 실제 학교가 있어도 데모를 함께 돌리는 게
RLS 격리 원칙상 안전하다고 판단해 `app/api/demo/seed/route.ts`의
"실제 학교가 있으면 409로 거부" 검사를 제거했다. `SEED_SECRET` 인증
검사는 그대로 유지(이게 진짜 보안 경계 — 아무나 못 누르게 막는 것).
README의 관련 문구도 함께 수정.

**검증**: tsc·eslint·vitest·build 전부 통과. 실제 배포에 반영되면
`/setup`에서 데모 데이터 만들기를 다시 눌러 성공하는지, 로그인 화면에
체험하기 버튼이 뜨고 실제로 한빛특수학교 데모 계정으로 들어가지는지는
**라이브에서 사용자가 직접 확인 필요**(이 세션엔 라이브 DB 없음).

### 14. [완료] 시간표 보기 학급 드롭다운 정렬, 특별실 예약 데모 확인

사용자 요청 두 가지.

### 15. [완료] 특별실 예약 색상 버그 — 탭 색을 칠하고 있었다

사용자가 "예약시 예약한 학교급에 따라 색이 다르게"를 다시 요청해서
`room-board.tsx`를 다시 열어보니, 지난 라운드(10번 항목)에서 이미
`COURSE_TONE`를 붙였다고 기록했지만 실제로는 **버그가 있었다**.

`ReservedCell`이 색을 정할 때 `COURSE_TONE[course]`의 `course`가 그
예약 자신의 과정이 아니라 **지금 보고 있는 탭**(`props.course`)이었다
— `<ReservedCell course={props.course} .../>`로 호출하고 있었다.
`Reservation` 타입에는 원래 자기 자신의 `course` 필드가 있는데
(`reservation.course`) 그걸 안 쓰고 있었던 것. 결과적으로 "고등" 탭을
보고 있으면 그 방에 잡힌 예약이 실제로는 초등 학급 것이든 전공과
것이든 전부 고등 색(파랑)으로 칠해졌다 — 탭을 바꿔야만 그 탭 색으로
전부 바뀌어 보였으니, 서로 다른 과정 예약을 한눈에 구분한다는 원래
목적이 무의미했다.

`course={props.course}` 인자를 없애고 `COURSE_TONE[reservation.course]`
로 직접 참조하도록 고쳤다. `devpreview-temp`에 `RoomBoard`를 목
데이터(같은 방, 같은 날 초등·중등·전공과 예약 3건을 "고등" 탭으로 보기)
로 렌더링해 Playwright 스크린샷으로 확인 — 탭은 고등(파랑)으로 켜져
있어도 1교시(초등)는 초록, 2교시(중등)는 하늘색, 3교시(전공과)는
보라로 각자 다르게 나오는 걸 눈으로 확인했다.

**검증**: tsc·eslint·vitest(87개)·build 전부 통과 + 위 스크린샷 확인.

### 16. [완료] 체험하기 되튕김 — 데모 시드의 프로필 insert가 에러를 씹고 있었다

체험하기가 "새로고침은 되는데 안 들어가진다"는 후속 보고. 3라운드째다 —
1차 서버 액션 캐시 의심, 2차 "실제 학교 있으면 데모 시드 거부" 차단
제거(15번 이전, 커밋 `b89e9bd`)까지 했는데도 재발. 이번엔 plan 모드로
전환해 Explore 에이전트로 RLS·시드·미들웨어를 전부 훑었다.

`app/login/actions.ts`의 `signInToDemo()`는 로그인 성공 후 `profiles`
조회가 비어 있으면 `redirect('/login?demo=blocked')`로 로그인 화면에
되돌린다 — 증상과 정확히 일치. 이게 나려면 "auth 계정은 있는데
`profiles` 행이 없는" 상태여야 하는데, `lib/demo/seed.ts`를 다시 보니
파일의 거의 모든 `.insert()`는 `{ error }`를 확인해 실패 시 던지는데
**딱 두 곳(DEMO_ACCOUNTS·EXTRA_STAFF의 profiles insert, 각각
`lib/demo/seed.ts:138`·`:167` 부근)만 에러를 안 봤다.** 이 insert가
조용히 실패하면 `auth.users`엔 계정이 남고 `profiles`엔 없는 고아
계정이 생겨 정확히 이 증상을 낸다 — 파일 맨 위 주석이 과거에 똑같은
증상을 겪었다고 적어 둔 것도 확인(그때는 정리 단계만 고치고 insert
쪽은 안 고쳤었다).

RLS(`is_active default true`), enum(`assistant`/`fixed_term` 전부
유효), `0014` 트리거(UPDATE 전용이라 INSERT 무관), 미들웨어(방금
로그인한 요청엔 타임아웃 쿠키가 없어 개입 불가)는 전부 코드 추적으로
배제했다 — 두 insert의 에러 무시가 가장 유력한 단일 원인.

두 곳 다 파일의 다른 insert와 같은 패턴(`const { error } = await
db.from('profiles').insert(...); if (error) throw new Error(...)`)으로
맞췄다. 로직을 바꾸는 게 아니라 숨어 있던 실패를 드러내는 것뿐이라
회귀 위험은 없다. 이제 프로필 생성이 실패하면 시드 전체가 명확한
에러로 멈추고, `app/api/demo/seed/route.ts`의 `describeError()`가
Postgres 에러의 message/details/hint/code를 `/setup` 화면에 그대로
보여주므로, 다음에 실패하면 이번엔 실제 원인이 화면에 뜬다.

**⚠️ 라이브 DB가 없어 이 세션에서 실제 재현·검증은 못 했다 — 사용자가
직접 이어서 해야 함**:
1. 배포 반영 후 `/setup`에서 "데모 데이터 만들기"를 **다시** 눌러야
   한다(`seedDemoSchool()`이 기존 데모를 지우고 처음부터 재생성하는
   구조라, 새로 돌려야 고아 계정이 청소됨).
2. 성공하면 로그인 화면 "체험하기"로 실제 대시보드까지 들어가는지 확인.
3. 이번에도 실패하면 화면에 뜨는 실제 에러 메시지를 알려주면 바로 다음
   원인으로 들어갈 수 있다.

**검증**: tsc·eslint·vitest(87개)·build 전부 통과. 실제 시드 실행·로그인
왕복은 라이브에서 사용자가 확인.

### 17. [완료] 진짜 원인 발견 — schema.sql이 청암학교 데이터를 지웠음, 안전장치 추가

16번 배포 후에도 여전히 로그인이 안 된다는 후속 보고. 이번엔 대화로
직접 증상을 좁혔다(라이브 접근이 없어 사용자가 화면에 보이는 것을
그대로 전해주는 방식으로 진행) — 체험하기뿐 아니라 **일반 로그인 폼으로
`admin@hanbit.demo`를 직접 타이핑해도 똑같이 튕겼다.** URL을 정확히
받아보니 `/dashboard`까지 갔다가 흰 화면 → 다시 로그인으로 돌아오는
패턴. 이건 로그인(서버 액션) 자체는 성공했는데 그 다음 `/dashboard`
레이아웃의 세션 확인이 실패한다는 뜻이었다.

결정적 단서: "예전에 청암학교 관리자로는 로그인이 잘 됐었나"라고
물으니 **"네, 전에는 잘 됐음"** — 즉 새로 생긴 회귀. "0014 마이그레이션을
어떻게 적용했나" 물으니 **"`supabase/schema.sql` 전체를 SQL Editor에
붙여넣어 실행함"**이라는 답이 나왔다. 바로 이거였다 — `schema.sql`은
맨 앞(`reset.sql`)에서 `public` 스키마의 모든 테이블을 `drop ... cascade`
후 다시 만든다. 파일 자체에 "실 데이터가 있는 학교에서는 절대 실행하지
마세요"라는 경고가 있었지만, 0014를 적용하는 방법으로 "`schema.sql`
또는 `0014_rls_hardening.sql`만" 둘 다 제시했었고 사용자는 자연스럽게
전자를 선택했다. `auth.users`(로그인 계정)는 별도 스키마라 안 지워졌지만
`public.profiles`·`public.schools`는 통째로 사라져, 로그인(auth)은
성공해도 "이 사람이 어느 학교 소속인지" 알려주는 행이 없어
`/dashboard`가 매번 로그인으로 돌려보낸 것 — 청암학교 관리자 계정도
데모 계정도 똑같이 이 증상을 보인 이유다.

**복구는 코드로 할 수 있는 부분이 아니라 사용자가 Supabase
대시보드에서 직접 해야 한다** — 채팅으로 안내함(고아가 된 auth 계정
삭제 → `/platform` 또는 `npm run school:new`로 학교 재개설 → 초대
수락으로 새 비밀번호 설정). 첫 스크린샷상 청암학교에 아직 학급·특별실
등록 전이었어서 실질 데이터 손실은 없어 보인다.

**재발 방지 — `supabase/reset.sql` 맨 앞에 안전장치 추가**:
```sql
do $$
begin
  if to_regclass('public.schools') is not null
     and exists (select 1 from public.schools where is_demo = false)
  then
    raise exception '실제 학교 데이터가 있어 멈췄습니다. ...';
  end if;
end $$;
```
`to_regclass()`로 테이블이 아직 없는 최초 설치 상황(정상 케이스)은
통과시키고, 이미 실제(비데모) 학교가 하나라도 있으면 `drop table`에
도달하기 전에 예외를 던져 막는다. `supabase/schema.sql`을 이 내용을
포함해 재생성했고, `README.md`의 "스키마 올리기" 절에도 "이미 실
데이터가 있으면 새로 추가된 마이그레이션 파일 하나만 실행하라"는
경고를 추가했다.

**검증**: SQL 문법은 정적으로만 확인(라이브 DB 없음). tsc·eslint·
vitest(87개)·build는 이 변경과 무관하지만 전부 재확인해 통과.

### 18. [완료] 진짜 결말 — 배포 지연이었다, 데모는 이미 복구됨 + 정리 루프 강화

17번에서도 여전히 로그인이 안 된다는 후속 보고가 왔고, "청암학교
관리자로도 안 된다"는 말에 한동안 세션 쿠키 유지 자체가 깨졌다는
가설로 진단용 임시 라우트(`/api/debug/session`)까지 만들어 배포하려던
참이었다. 그런데 사용자가 Vercel 배포 로그와 실제 배포본을 직접 확인해
**진짜 원인**을 가져왔다:

- 그동안 `hanarum.vercel.app`이 서비스하던 건 16번 수정(고아 프로필
  insert 에러 처리, 커밋 `3fae7a1`)과 17번 수정(reset.sql 안전장치,
  커밋 `5d27ca1`)이 **아직 반영 안 된 이전 커밋(`8293edc`)**이었다 —
  즉 그동안 재현·진단한 "로그인 실패"는 전부 고쳐지기 전 코드를 테스트한
  결과였다.
- 화면에서 "새로고침만 되는 것"처럼 보인 이유도 확인됨: 서버 500 에러가
  아니라 로그인 서버 액션이 `303 Redirect`로 `/login`을 돌려준 것 —
  Vercel 로그에 `POST /login 303 → GET /login 200`이 반복 기록됨.
- 최신 커밋(`5d27ca1`)이 실제 반영된 뒤 사용자가 배포본에서 직접
  확인: "일반 교사로 체험하기"(민아름 실무사)·"관리자(교감) 정한결"
  둘 다 `/dashboard` 진입 성공. **16·17번 수정이 정확히 맞는 진단이었고
  실제로 문제를 고쳤다** — 세션 쿠키 문제는 없었다.

즉시 임시 진단 라우트는 필요 없어져 커밋 전에 지웠다(`app/api/debug/`,
`middleware.ts`의 `PUBLIC_PATHS` 추가분 모두 원상복구).

**진짜 남은 문제 하나**: 사용자가 `lib/demo/seed.ts`의 정리(cleanup)
루프를 다시 봐 달라고 지적함 — 기존 데모 계정을 지우는 부분이
`await db.auth.admin.deleteUser(demoUser.id).catch(() => undefined)`로
실패를 완전히 무시하고 있었다. 하나라도 실패하면 그 auth 계정은 남은
채로 바로 다음 줄에서 `schools` 행을 지워버려(cascade로 profiles만
사라짐) **16번에서 고친 것과 정확히 같은 종류의 고아 계정**이 다시
생길 수 있는 구조였다 — 이번엔 insert가 아니라 delete 쪽에서.

고침: 삭제 실패를 배열에 모아두고, **하나라도 실패했으면 학교 삭제로
넘어가지 않고 바로 에러를 던져 시드 전체를 멈춘다.** 모든 auth 계정
삭제가 확인된 뒤에만 `schools` 삭제로 진행한다 — 정리가 끝났다는
확신이 서기 전에는 다음 단계로 안 넘어가는 것.

**정식 운영 데이터 관련 남은 확인사항** (사용자에게 안내):
- schema.sql 재실행으로 청암학교의 `profiles`·`schools`·업무 데이터가
  지워진 사고 자체는 여전히 유효한 사실이다 — 데모가 복구됐다고 이게
  자동으로 없어지진 않는다. 별도 백업이 있다면 복원 여부를 확인하고,
  없다면 이전에 안내한 절차(고아 auth 계정 정리 → 학교 재개설 → 초대
  수락)로 청암학교를 다시 만들어야 한다.
- `schema.sql`은 이제부터 운영 중인 프로젝트에 다시 실행하면 안 되고
  (17번에서 안전장치를 넣긴 했지만), 새 변경분은 항상
  `supabase/migrations/`의 개별 파일만 적용해야 한다.

**검증**: tsc·eslint·vitest(87개)·build 전부 통과. cleanup 루프 자체는
라이브 DB가 없어 실행 검증은 못 함 — 다음 데모 재시드 때 정상 동작
확인 필요.

### 19. [완료] 무한 리다이렉트 함정 — "모바일은 되는데 노트북은 안 됨"의 정체

18번 이후에도 "여전히 같은 문제"라는 보고. 결정적 단서는 사용자가 던진
한 마디였다 — **"모바일에서는 되는데 노트북에서는 안 되는 이유는?"**
같은 배포·같은 DB인데 기기에 따라 갈린다면 서버 데이터 문제가 아니라
그 브라우저에 남은 상태, 즉 **쿠키** 문제다.

기전은 코드로 정확히 재구성된다. 노트북에는 `schema.sql` 실행 **전에**
청암학교 관리자로 로그인했던 세션 쿠키가 남아 있었다. `schema.sql`은
`public` 스키마만 지우고 `auth.users`는 건드리지 않으므로 **그 쿠키는
여전히 유효**하다. 그래서:

1. `middleware.ts` — 로그인된 사용자가 `/login`에 오면 `/dashboard`로 보냄
2. `app/(app)/layout.tsx` — `getSessionContext()`가 프로필을 못 찾아
   (`profiles` 행이 지워졌으니) `/login`으로 되돌림
3. → 1번으로 → **무한 루프**

체험하기를 눌러도 이 루프에 갇혀 화면만 깜빡였다. 모바일은 그 옛 쿠키가
없어서 멀쩡히 동작했다 — 두 기기의 차이가 정확히 이것이었다.

**즉시 조치**(사용자): 노트북에서 `hanarum.vercel.app` 쿠키 삭제.

**코드 수정** — 이건 브라우저 탓으로만 넘길 게 아니라 명백한 결함이다.
프로필이 사라진 계정은 **로그아웃 버튼조차 누를 수 없이** 갇힌다(로그아웃
화면 자체가 로그인 뒤에 있으므로). 탈출구를 만들었다:

- **`app/logout/route.ts` 신규** — `signOut()`으로 세션을 끊고
  `/login?reason=stale`로 보낸다. 왜 서버 액션이 아니라 **라우트
  핸들러**인가: 서버 컴포넌트에서는 쿠키를 못 쓴다
  (`lib/supabase/server.ts`의 `setAll`이 그 예외를 삼킨다) — 그래서
  레이아웃에서 `signOut()`을 불러도 쿠키가 안 지워진다. 라우트 핸들러는
  쿠키를 쓸 수 있다. 게다가 `signOut()`이 네트워크 오류로 실패해도
  `sb-*`·`ha_activity` 쿠키를 **직접 만료시키는 안전장치**를 넣었다 —
  여기서 500을 내면 사용자는 갇힌 채로 남는데 그게 제일 나쁘다.
- **`app/(app)/layout.tsx`** — 세션이 없으면 `/login`이 아니라
  `/logout`으로 보낸다. 여기까지 왔다는 건 미들웨어는 로그인으로 봤는데
  프로필을 못 찾았다는 뜻이라, `/login`으로 보내면 루프가 된다.
- **`middleware.ts`** — `/logout`을 `PUBLIC_PATHS`에 추가. 세션을 끊으러
  가는 길목이 세션을 요구하면 세션이 망가진 사람은 영영 못 빠져나온다.
- **`app/login/page.tsx`** — `reason=stale` 안내 문구 추가.

**함께 고친 것 — 18번 수정의 순서 결함**: 18번에서 "삭제 실패 시 학교를
지우기 전에 예외를 던지도록" 했는데, `profiles.id`가
`references auth.users(id) on delete cascade`(`0001_core.sql:61`)라
auth 계정을 먼저 지우면 프로필이 함께 사라진다. 즉 중간에 멈추면 "학교
행은 남았는데 프로필은 대부분 사라진" 반쯤 부서진 상태가 되고, 로그인
화면은 학교 존재 여부만 보고 체험하기 버튼을 띄우므로(`hasDemoSchool`)
**버튼은 보이는데 눌러도 안 들어가지는** 상태가 된다 — 이번 증상과
똑같은 모습이다. 순서를 뒤집어 **학교를 먼저 지우고** 그 다음 auth
계정을 지우도록 바꿨다(최악의 경우에도 "데모 없음"이라는 깨끗한 상태로
끝나 버튼 자체가 안 나온다). 삭제도 두 번까지 시도하고, 반환값을 믿는
대신 목록을 다시 읽어 정말 사라졌는지 확인한다.

**검증**: tsc·eslint·vitest(87개)·build 통과에 더해, **이번엔 라이브
동작까지 실제로 확인함** — 더미 `.env.local`로 `next build && next start`
후 스테일 쿠키를 들려 `/logout`을 호출했더니 `303 → /login?reason=stale`,
`sb-...=; Expires=Thu, 01 Jan 1970`, `ha_activity=; Expires=...`로
쿠키가 확실히 만료됐다. Supabase가 닿지 않는 더미 환경이라 `signOut()`은
실패했는데도 안전장치 덕에 탈출이 보장되는 것까지 확인됐다.
`/login?reason=stale` 안내 문구 렌더링도 확인.

### 20. [완료] 데모 재시드 때 학교 공용 AI 키를 이어받도록 수정

19번 이후에도 여전히 그 노트북에서만 안 된다는 보고가 이어져(다른
브라우저·다른 네트워크에서도 재현, 모바일은 계속 정상) 진단 화면까지
만들려던 참이었는데, 사용자가 방향을 바꿔 **"체험하기에서 관리자가
등록해 둔 Gemini·유튜브 키를 유지해 줄 수 있냐"**고 물었다(노트북 문제
자체는 잠시 보류 — 다음에 이어서 파야 함, 아래 "막혀 있는 것" 참고).

확인해보니 실제로 문제였다 — `seedDemoSchool()`이 기존 데모 학교를
지우고 완전히 새 `schools` 행을 만드는데, 그때 `gemini_key_enc` 등
키 컬럼은 채우지 않아 매번 빈 채로 새로 생겼다. 데모는 매일 새벽
자동으로 재시드되므로, 관리자가 전날 애써 등록한 학교 공용 키가 다음
날이면 사라져 체험하는 사람이 수업 도구함(AI)에서 "키가 없습니다"만
보게 되는 구조였다.

`lib/demo/seed.ts`에서 기존 데모 학교를 지우기 **직전**에
`gemini_key_enc`·`gemini_key_hint`·`youtube_key_enc`·`youtube_key_hint`
네 컬럼을 미리 읽어 두고(암호문 그대로, 복호화하지 않음), 새 학교를
`insert`할 때 그대로 넣어준다. 키가 있으면 시드 로그에도
"이전 데모 학교의 학교 공용 Gemini·유튜브 키를 이어받았습니다"로
남겨 `/setup` 화면에서 확인할 수 있게 했다. 개인 키(`profiles`의
같은 컬럼)는 대상이 아니다 — 애초에 매번 새로 만들어지는 개인 계정에
붙는 값이라 이어받을 "이전 나"가 없다.

**검증**: tsc·eslint·vitest(87개)·build 전부 통과. 라이브 DB가 없어
실제 키 이어받기 왕복은 다음 데모 재시드 때 확인 필요.

### 막혀 있는 것 — 그 노트북에서만 체험하기가 안 되는 문제 (미해결)

19번 수정(무한 리다이렉트 탈출구, 쿠키 삭제 안내) 이후에도 재현됨.
좁혀진 사실:
- 같은 배포·같은 데이터에서 **모바일은 항상 정상**
- 문제의 노트북은 **브라우저를 바꿔도**(크롬↔엣지 등) 재현
- **네트워크를 바꿔도**(집 와이파이 ↔ 휴대폰 핫스팟) 재현 — 모바일은
  같은 핫스팟에서도 정상이라 네트워크 자체는 무죄
- 데모 재시드는 매번 성공(계정 25개 요약이 정상적으로 뜸)
- 체험하기를 누르면 최종적으로 `?next=%2Fdashboard`로 끝남 — 이건
  `signInToDemo()`의 `demo=blocked`/`demo=missing`이 아니라
  **미들웨어 자체가 "로그인 안 됨"으로 판정**했다는 뜻. 즉 로그인
  서버 액션은 성공하는데 그 세션이 다음 요청에서 전혀 인식되지 않음

브라우저·네트워크 둘 다 무죄로 나온 이상 남은 건 그 노트북에만 있는
무언가(시계는 확인해 자동·정확함, 확장프로그램·백신 등 로컬 보안
소프트웨어는 미확인)다. 개발자도구(F12 → Application → Cookies)로
체험하기 직후 `sb-`로 시작하는 쿠키가 실제로 찍히는지 확인해 달라고
요청했으나 아직 답을 못 받은 상태 — **다음 세션에서 이어서 진단할 것.**
필요하면 쿠키 이름·`auth.getUser()` 성공 여부만 텍스트로 보여주는
임시 진단 라우트(`/api/debug/session` 형태, 이전에 설계했다가 배포
전 취소함)를 다시 만들어 배포하는 게 다음 단계로 유력하다.

사용자에게 요청한 상태.** 다음 세션에서 이 제약이 풀렸는지 다시 시도해보고,
안 풀렸으면 계속 사용자 확인에 의존해야 함.

3. `Database` 타입을 `interface`로 선언해 supabase-js 제네릭 제약(`Record<string, GenericSchema>`)을 통과 못 함 → **모든 쿼리가 조용히 `never`로 무너지고 있었음**(런타임은 동작하지만 타입 안전성 전무). `type`으로 바꿔 해결

## 아직 안 만든 것

**Phase 0~4는 전부 구현 완료.** Phase 5 항목 중 안전 프로토콜·PBS·IEP도
모두 구현됐다(위 "Phase 5 진행 중" 절 참고) — `lib/security/
sensitivity.ts`에 `planned: true`로 남은 메뉴 항목은 이제 없다. 이 절의
나머지는 Phase 5 시작 전 시점 기록이라 시간표 엑셀 업로드·세션 타임아웃
등 이후 완료된 항목이 아래에도 남아 있을 수 있다 — 최신 상태는 이 문서
맨 위 "Phase 5 진행 중" 절을 우선 참고할 것.

- **승인 채널 화이트리스트**(수업 자료 찾기) — Phase 4에서 의도적으로
  뺌. 위 "Phase 4" 절 참고
- **부적절 영상 신고 버튼**(수업 자료 찾기) — 관리자 검토 큐가 없어서
  뺌
- **엑셀/CSV 업로드**(Phase 0 계획에 있었으나 계속 범위에서 빠짐) —
  지금은 관리자 화면 수동 입력 또는 시드 스크립트로만 데이터가 들어감
- **나이스 학사일정 자동 동기화** — `academic_events.source`/`source_key` 컬럼은 있지만 동기화 배치 없음
- **웹푸시/이메일 알림**
- **세션 타임아웃 실제 적용** — `lib/security/sensitivity.ts` 의
  `SESSION_TIMEOUT_MIN` 상수는 있지만 어디서도 실제로 강제하지 않음
  (민감구역 20분 등). 값만 정의돼 있고 미들웨어·레이아웃에 연결 안 됨
- Playwright e2e 테스트 (`npm run test:e2e` 스크립트는 있으나 테스트 파일 없음)

계획서의 "추가 제안 기능"(Phase 5 후보) 중 남은 것: 보조인력 배치표,
교구·보조공학기기 대여 관리, 현장체험학습 계획·안전점검, 통학버스
관리, 가정통신문 발송·확인, AAC 의사소통판 생성기, 학급 일지, PWA
설치, WCAG 접근성 강화 등. 우선순위는 아직 정해지지 않음 — 다음
세션에서 사용자와 상의 필요.

| 항목 | 한도 | 이 앱 기준 체감 |
|---|---|---|
| Supabase DB | 500MB | 학교 수십 곳 분량, 병목 아님 |
| Supabase MAU | 50,000명 | 학교 수백 곳 분량, 병목 아님 |

| Vercel 함수 실행시간 | 60초(기본)/300초(Fluid Compute) | `/api/demo/seed`(maxDuration=300)에 해당. Fluid Compute 미적용 시 시드가 타임아웃 날 수 있음 — 배포 후 실제로 확인 필요 |

Vercel 대역폭보다 **Hobby 약관(비상업적 용도)**이 먼저 걸리는 제약이라는
점을 사용자에게 이미 안내함.
